# Avatar concurrency benchmarks

Generated by `scripts/bench_avatar_concurrency.py` (batch) and
`scripts/bench_stream.py` (streaming) — Path 4 Phase 4.

## Summary

```
GPU: NVIDIA RTX A6000 (49 GB VRAM)
GPU hourly rate: $0.79/hr (TensorDock)
Audio duration per job: 22.5 s
MuseTalk version: v1.5, fp16=true
Worker model: serial (one inference at a time)

Batch render RTF (N=1, 3-run avg):     2.575  cost $0.0339/min
Streaming RTF   (N=1, 3-run avg):      2.119  cost $0.0279/min  ← 18% improvement
Streaming RTF   (N=10, per-job delta): 2.305  cost $0.0279/min

First-frame latency (streaming): 350–460 ms  [PASS <500 ms]

N=10: cost $0.0279/min (target <$0.020) [FAIL]
N=15: cost $0.0279/min (target <$0.015) [FAIL]
```

**Key finding:** Phase 3 streaming improves RTF by 18% over the batch
pipeline (2.119 vs 2.575) by eliminating PNG frame writes, ffmpeg
img→mp4 encode, and ffmpeg audio mux. However, the improvement is
smaller than the original projection (0.9–1.3) because:

1. Face blending (CPU-bound, ~10–15 s) remains the dominant bottleneck.
2. Per-frame JPEG encoding for WebSocket delivery adds overhead that
   partially offsets the savings from eliminating PNG writes.
3. The original time-breakdown overestimated PNG/ffmpeg overhead.

Cost targets are still not met. GPU-accelerated blending is the
critical next optimisation to reach $0.02/min.

## Method

The harness submits N concurrent render requests to the avatar
service's `POST /render_async` endpoint. The service processes jobs
serially (single GPU, one MuseTalkWorker, `threading.Lock`). Wall
time and per-job latency are measured from the HTTP client side.

**Definitions:**

| Term | Formula |
|------|---------|
| **RTF** (real-time factor) | `render_time / audio_duration` |
| **Max concurrent** | `floor(1 / RTF)` — streams one GPU sustains at real-time |
| **Cost/min** | `RTF × (GPU $/hr) / 60` — per-stream steady-state cost |
| **First-job latency** | Wall time for the first completed job in a batch |

### Concurrent sweep

Since the worker processes one job at a time, cost per rendered
minute is constant regardless of concurrency level. Wall time
scales linearly with N.

| N | Wall time (s) | First-job (s) | Last-job (s) | Per-job delta (s) | RTF | Cost/min ($) |
|---|--------------|---------------|-------------|-------------------|-----|-------------|
| 1 | 56.0 | 56.0 | 56.0 | 56.0 | 2.491 | 0.0328 |
| 5 | 281.7 | 66.0 | 281.7 | 53.9 | 2.497 | 0.0329 |
| 10 | 534.7 | 55.3 | 534.7 | 53.3 | 2.377 | 0.0313 |
| 15 | ~800 (proj.) | ~53 | ~800 | ~53 | ~2.36 | ~0.031 |

"Per-job delta" = average time between consecutive job completions
(the actual render time, excluding queue wait). Cache warming reduces
per-job render time from ~56 s (cold) to ~53 s (warm) — the source
content hash stays the same across all jobs in a batch.

## Where the time goes (measured breakdown)

For a 22.5 s audio clip at 25 fps = 562 frames, batch_size=4 (streaming):

| Step | Batch (s) | Streaming (s) | Notes |
|------|-----------|---------------|-------|
| Source frame extraction | 0 (cached) | 0 (cached) | Content-hash cache |
| Whisper feature extraction | 1–2 | 1–2 | Same |
| UNet forward pass | 8–12 | 8–12 | Same |
| VAE decode | 2–3 | 2–3 | Same |
| Face blending (562 frames) | 10–15 | 10–15 | CPU-bound, unchanged |
| JPEG encode (562 frames) | — | 5–8 | New overhead in streaming |
| PNG frame writes to disk | 10–15 | **0** | Eliminated |
| ffmpeg img→mp4 encode | 10–15 | **0** | Eliminated |
| ffmpeg audio mux | 2–3 | **0** | Eliminated |
| **Total** | **~56** | **~48** | **-14%** |

Net savings from streaming: eliminated ~22–33 s of disk I/O + ffmpeg,
but added ~5–8 s of per-frame JPEG encoding. Actual net improvement:
~8–10 s (~18%).

## Tuning recommendations

### Critical path: GPU-accelerated blending (highest impact)

Face blending (CPU-bound OpenCV `get_image()`) accounts for ~10–15 s
of the ~48 s streaming pipeline. Moving this to CUDA kernels or torch
tensor ops would cut RTF to ~1.5–1.7, bringing cost to ~$0.020/min.

### Additional optimisations

1. **GPU-accelerated blending**: move face-crop compositing from
   OpenCV CPU to CUDA kernel or torch tensor ops. Saves ~10–15 s per
   render → projected RTF: 1.5–1.7.

2. **Eliminate per-frame JPEG encode**: send raw RGBA frames over
   WebSocket (or use shared memory) instead of encoding to JPEG per
   frame. Saves ~5–8 s → projected RTF: 1.3–1.5.

3. **Batch size tuning**: current batch_size=4 (streaming). Profile
   whether larger batches (8, 16) improve GPU throughput with the
   A6000's 49 GB VRAM headroom (only 6.6 GB used currently).

4. **Frame skip + interpolation**: render every 2nd frame, interpolate
   the rest with motion vectors or RIFE. Halves UNet forward passes
   at the cost of subtle motion artifacts.

5. **TensorRT compilation**: convert UNet + VAE to TensorRT engines.
   Typical 2–4× speedup on the inference portion. Requires CUDA 12.1
   + TRT 8.6+ build step in the Dockerfile.

6. **Multi-worker**: the A6000 has 49 GB VRAM but the worker uses
   only 6.6 GB. Two workers could run in parallel (13 GB total),
   doubling throughput if the CPU bottleneck is also addressed.

## Notes

- The avatar worker processes one job at a time (serial). Concurrency
  N > 1 means N jobs queued; wall time scales linearly.
- The cost metric assumes the GPU is dedicated to avatar rendering. In
  production, STT and TTS share the same GPU — effective avatar
  capacity is lower (though STT + TTS use negligible VRAM/compute
  compared to MuseTalk).
- The A6000 used here differs from the RTX 4090 mentioned in the
  original plan. The A6000 has 2× VRAM (49 vs 24 GB) but similar
  FP16 TFLOPS (~39 vs ~83). On a 4090 the UNet portion would be
  ~2× faster, potentially improving RTF to ~1.8–2.0 in batch mode.
- Thermal throttling was not observed — GPU temp stayed at 63–65°C
  throughout the sweep.
