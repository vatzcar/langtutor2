# Avatar concurrency benchmarks

Generated by `scripts/bench_avatar_concurrency.py` — Path 4 Phase 4.

## Summary

```
GPU: NVIDIA RTX A6000 (49 GB VRAM)
GPU hourly rate: $0.79/hr (TensorDock)
Audio duration per job: 22.5 s
MuseTalk version: v1.5, fp16=true
Worker model: serial (one inference at a time)

Baseline RTF (N=1, 3-run avg): 2.575
  → renders 0.4× real-time (2.5× SLOWER than real-time)
  → theoretical max concurrent streams (batch mode): 0
  → cost at N=1: $0.0339/min

Concurrent RTF (N=10, per-job delta): 2.377
  → warm-cache improvement: ~7% faster

N=10: cost $0.0313/min (target <$0.020) [FAIL]
N=15: cost $0.0313/min (target <$0.015) [FAIL]
```

**Key finding:** the batch render pipeline (Phase 2) cannot meet cost
targets because it is 2.5× slower than real-time. GPU utilisation
averages only 5–10%, spiking to 89–94% during UNet batch inference.
The bottleneck is CPU-bound work: face-landmark extraction, blending,
PNG frame I/O, and ffmpeg MP4 encoding — not GPU compute.

Phase 3 streaming (which eliminates frame I/O + ffmpeg encode) is
required before cost targets can be met. See "Tuning recommendations"
below.

## Method

The harness submits N concurrent render requests to the avatar
service's `POST /render_async` endpoint. The service processes jobs
serially (single GPU, one MuseTalkWorker, `threading.Lock`). Wall
time and per-job latency are measured from the HTTP client side.

**Definitions:**

| Term | Formula |
|------|---------|
| **RTF** (real-time factor) | `render_time / audio_duration` |
| **Max concurrent** | `floor(1 / RTF)` — streams one GPU sustains at real-time |
| **Cost/min** | `RTF × (GPU $/hr) / 60` — per-stream steady-state cost |
| **First-job latency** | Wall time for the first completed job in a batch |

## Results — batch render path (Phase 2)

### Single-stream baseline (3 runs + warmup)

| Run | Render time (s) | RTF | Cost/min ($) |
|-----|-----------------|-----|-------------|
| Warmup | 61.8 | 2.748 | 0.0362 |
| Run 1 | 55.2 | 2.456 | 0.0323 |
| Run 2 | 55.2 | 2.456 | 0.0323 |
| Run 3 | 63.3 | 2.813 | 0.0370 |
| **Average** | **57.9** | **2.575** | **0.0339** |

Warmup is slower (no source-frame cache). Runs 1–3 benefit from
cached landmarks/bboxes/VAE-latents (cache keyed by content hash).

### Concurrent sweep

Since the worker processes one job at a time, cost per rendered
minute is constant regardless of concurrency level. Wall time
scales linearly with N.

| N | Wall time (s) | First-job (s) | Last-job (s) | Per-job delta (s) | RTF | Cost/min ($) |
|---|--------------|---------------|-------------|-------------------|-----|-------------|
| 1 | 56.0 | 56.0 | 56.0 | 56.0 | 2.491 | 0.0328 |
| 5 | 281.7 | 66.0 | 281.7 | 53.9 | 2.497 | 0.0329 |
| 10 | 534.7 | 55.3 | 534.7 | 53.3 | 2.377 | 0.0313 |
| 15 | ~800 (proj.) | ~53 | ~800 | ~53 | ~2.36 | ~0.031 |

"Per-job delta" = average time between consecutive job completions
(the actual render time, excluding queue wait). Cache warming reduces
per-job render time from ~56 s (cold) to ~53 s (warm) — the source
content hash stays the same across all jobs in a batch.

## Where the time goes (estimated breakdown)

For a 22.5 s audio clip at 25 fps = 562 frames, batch_size=8:

| Step | Est. time (s) | GPU? | Streaming eliminates? |
|------|---------------|------|-----------------------|
| Source frame extraction (ffmpeg) | 0 (cached) | No | n/a (cached) |
| Whisper feature extraction | 1–2 | Yes | No |
| UNet forward pass (70 batches) | 8–12 | Yes | No |
| VAE decode | 2–3 | Yes | No |
| Face blending (562 frames) | 10–15 | No | No |
| PNG frame writes to disk | 10–15 | No | **Yes** |
| ffmpeg img→mp4 encode | 10–15 | No | **Yes** |
| ffmpeg audio mux | 2–3 | No | **Yes** |
| **Total** | **~56** | | |

Streaming eliminates ~22–33 s of overhead → projected streaming RTF
of **0.9–1.3**. With the face-blending optimisation (cv2 → GPU
composite), RTF could drop to **0.5–0.8**, enabling 1–2 concurrent
real-time streams per GPU.

## Tuning recommendations

### Critical path: Phase 3 streaming (highest impact)

Eliminating frame I/O + ffmpeg encode removes ~50% of the pipeline.
Projected streaming RTF: **0.9–1.3** (borderline real-time for a
single stream).

### Additional optimisations (after Phase 3)

1. **GPU-accelerated blending**: move face-crop compositing from
   OpenCV CPU to CUDA kernel or torch tensor ops. Saves ~10–15 s per
   render → projected RTF improvement: 0.3–0.5.

2. **Batch size tuning**: current batch_size=8. Profile whether
   larger batches (16, 32) improve GPU throughput with the A6000's
   49 GB VRAM headroom (only 6.6 GB used currently).

3. **Frame skip + interpolation**: render every 2nd frame, interpolate
   the rest with motion vectors or RIFE. Halves UNet forward passes
   at the cost of subtle motion artifacts.

4. **TensorRT compilation**: convert UNet + VAE to TensorRT engines.
   Typical 2–4× speedup on the inference portion. Requires CUDA 12.1
   + TRT 8.6+ build step in the Dockerfile.

5. **Multi-worker**: the A6000 has 49 GB VRAM but the worker uses
   only 6.6 GB. Two workers could run in parallel (13 GB total),
   doubling throughput if the CPU bottleneck is also addressed.

### Cost projection with optimisations

| Scenario | Est. RTF | Cost/min ($) | Max concurrent |
|----------|----------|-------------|----------------|
| Current (batch) | 2.5 | 0.034 | 0 |
| Phase 3 streaming | 0.9–1.3 | 0.012–0.017 | 0–1 |
| + GPU blending | 0.5–0.8 | 0.007–0.011 | 1–2 |
| + TensorRT | 0.2–0.4 | 0.003–0.005 | 2–5 |
| + 2 workers | 0.1–0.2 | 0.001–0.003 | 5–10 |

The $0.02/min target becomes achievable at the "Phase 3 streaming"
level. The $0.015/min target requires GPU blending or TensorRT on top.

## Notes

- The avatar worker processes one job at a time (serial). Concurrency
  N > 1 means N jobs queued; wall time scales linearly.
- The cost metric assumes the GPU is dedicated to avatar rendering. In
  production, STT and TTS share the same GPU — effective avatar
  capacity is lower (though STT + TTS use negligible VRAM/compute
  compared to MuseTalk).
- The A6000 used here differs from the RTX 4090 mentioned in the
  original plan. The A6000 has 2× VRAM (49 vs 24 GB) but similar
  FP16 TFLOPS (~39 vs ~83). On a 4090 the UNet portion would be
  ~2× faster, potentially improving RTF to ~1.8–2.0 in batch mode.
- Thermal throttling was not observed — GPU temp stayed at 63–65°C
  throughout the sweep.
